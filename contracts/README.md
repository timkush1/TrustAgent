# contracts/

The single source of truth that the Go proxy, the Python engine and the React dashboard (plus the
static site) share: JSON Schemas, the configuration key registry, evaluator templates, question sets,
policies, detector and evidence rules, prompts, prices, value claims, demo scenarios, UI copy, API
fixtures and golden vectors. The normative description is `docs/v2/SPEC.md` §7.6; this file explains
how to work with the directory.

Go is the reference implementation. TypeScript conforms to it through golden vectors. Python runs only
the `cost` vectors.

## Layout

|---|---|---|

| `config/keys.v1.json` | Every configuration key: name, aliases, services, kind, default, secret, advanced, restart, group, description (SPEC §2.7) | `keys.v1` |
| `evaluators/<id>.v<N>.json` | Built-in evaluator templates (SPEC §2.8) | `evaluator.v1` |

Schemas without a committed instance describe documents produced elsewhere: `decision.v1` (a stored
gate decision), `decide-input.v1` (the input of `decide()`, also used by `decide` vectors),
`evidence-summary.v1`, `evaluator-draft.v1` (Studio drafts), `calibration.v1` (`config/calibration/`),
`recording.v1` (replay manifests) and `benchmark-run.v1` (`docs/benchmarks/results/`).
`common.v1` holds the shared enums and primitives every other schema references.
`api.v1.schema.json` (REST and WebSocket bodies) is generated by the API types stream.

Empty directories carry a `.gitkeep` so the Go embed patterns stay valid.

## Who loads what

- **Go**: `backend-go/go.mod` requires `github.com/truthtable/contracts v0.0.0` with
  `replace github.com/truthtable/contracts => ../contracts`, and reads files from `contracts.FS` by path
  (`contracts.FS.ReadFile("config/keys.v1.json")`). Images build from the repository root, so the
  replace path resolves in Docker as well.
- **Python**: `truthtable/contracts.py` resolves `TRUTHTABLE_CONTRACTS_DIR`, then walks up from the
  package to a `contracts/` directory, then falls back to `/app/contracts` (the engine image copies the
  directory there).
- **TypeScript**: the Vite alias `@contracts` points at `../contracts` (with `server.fs.allow`), and JSON
  is imported statically. Types are generated from the schemas with `json-schema-to-typescript` into
  `src/lib/contracts/types.gen.ts` (committed; CI checks for drift). Schema titles become the type names
  (`EvaluatorSpec`, `EvaluatorDraft`, `PolicyDoc`, `RouteSettings`, `RouteEvaluatorRef`,
  `CalibrationFile`, `CalibrationEntry`, `BenchmarkRun`, ...).

## Conventions

- **File names** carry the document version: `<name>.v<N>.json`. A schema's `$id` is
  `https://github.com/timkush1/TrustAgent/contracts/schema/<file name>`; `$ref`s between schemas are
  relative file names, so they resolve both online and from disk.
- **Regular expressions** in schemas and rules are RE2- and ECMAScript-compatible: no lookaround, no
  backreferences, flags passed separately. (The patterns in `superseded.v1.json` are the exception:
  they are ECMAScript-only and used only by the Node check.)
- **Canonical JSON, money, time and text offsets** follow SPEC §2.1: RFC 8785 (JCS), `*_usd` floats,
  RFC 3339 UTC timestamps ending in `Z`, UTF-16 half-open offsets.
- **Placeholders** in UI copy use `{name}`. `{command:<id>}` renders a command from `ui/commands.v1.json`
  and `{claim:<id>}` renders a value claim with its label chip. The validator resolves both.
- **Every number shown to users has a label**: `measured`, `estimate`, `third_party`, `vendor` or
  `simulated`. Estimates reference a figure in `pricing/assumptions.v1.json`; the validator recomputes
  every figure from its terms and the price table and fails when the stated value drifts. Vendor prices
  must equal the price table. Measured claims carry no value: it comes from `claims/measured.json`, and
  `empty_display` ("not yet measured") is shown until a measured run exists. A price note starting with
  `[A]` is an assumption that must be re-verified before `make bench-publish`.

## Versioning

- A document type's version (`v1`) changes only on a breaking change. A breaking change adds a new
  schema file (`evaluator.v2.schema.json`) next to the old one; loaders accept both until the old one is
  retired. Additive, optional fields may be added within a version when every runner tolerates them.
- **Evaluator templates are immutable once released.** Changing a question, a criterion or a signal
  changes the calibration key, so it ships as a new version file (`groundedness.v2.json`) with a
  `parent` and `changelog`; policies pin `<id>@<version>` and `@latest` is forbidden.
- `config/keys.v1.json` and the UI files evolve in place; removing or renaming a key is a breaking change
  recorded in the CHANGELOG and, when the old name must never come back, in `superseded.v1.json`.
- The project version itself lives in `VERSION`; `package.json` here is private and stays `0.0.0`.

## Golden vectors: draft to frozen

A vector file is `{"vector":"1","kind","name","status","input","expected","tolerance"?}` stored as
`vectors/<kind>/<name>.json`, where `kind` equals the directory and `name` equals the file name.
Known kinds: `canonical`, `tokens`, `question_hash`, `normalize`, `compile`, `decide`,
`calibration_apply`, `calibrate_fit`, `detectors`, `evidence`, `lint`, `cost`, `pkce`. An unknown kind
fails every runner.

1. **draft**: hand-authored semantic vectors, and new cases, start as `draft`. `expected` may be a
   subset of the output. Numbers compare as parsed values within `tolerance` (default `1e-9`); strings
   and arrays compare exactly.
2. **generated**: Go `cmd/vectorgen` (`make vectors`) fills in mechanical `expected` values
   and records `generated_by`. A person reviews the diff.
3. **frozen**: once the Go reference passes the vector and the review is done, `status` becomes `frozen`.
   A frozen vector never changes. A behaviour change adds a new vector (and, if needed, a new evaluator
   or schema version).

`decide` vector inputs are validated against `decide-input.v1`, and `lint` vector specs against `evaluator.v1`.
`make vectors` also checks the hand-written kinds that have a Go runner (`decide`, `detectors`) against the
reference, but never writes their `expected`. The per-kind `input`/`expected` formats, and the SPEC readings the draft vectors pin, are in
[`vectors/README.md`](vectors/README.md).

## Presets

`policies/presets.v1.json` holds the route presets the Policies page offers. A preset is a partial
`RouteSettings` that the page merges over the route the way a route merges over `defaults` (objects key by
key, arrays replace), so a preset without `evaluators` keeps the route's own; `validate.mjs` checks each one
merged over the schema defaults. The first three are the SPEC §2.7 presets; the others
start from the SPEC's own examples (the `support-bot` and `payments-faq` routes and the `rubric-only`
question set).

| Preset | Mode | What it sets |
|---|---|---|
| `observe-all` | observe | every request checked (`sample_rate: 1`); answers never change |
| `flag-risky` | flag | flag mode only, keeping the route's evaluators |
| `block-contradictions` | block | groundedness and contradiction, buffered streams, `require_calibration`; starts as Flag until calibrated |
| `support-bot` | flag | groundedness, contradiction and commitments, with off-brand tone in shadow; fill in the two params |
| `rubric-only` | flag | the `rubric-only` set (refusal, unsafe policy, PII or secret leak, injection success) for apps without documents |
| `replace-unverified` | fallback | the `payments-faq` settings, keeping the route's evaluators: fail closed, buffered, 1.5 s deadline with a 400 ms hedge, no `request_context` evidence, URL and citation detectors block, fallback answer from documents only, then block |

## Prompts

`prompts/<id>.v<N>.json` (`prompt.v1`) is an LLM prompt that every sender uses unchanged: the engine's
`DraftEvaluator` (`truthtable/studio/drafter.py`) and the static build's Studio send
`evaluator-drafter.v1.json`.

- `system`, `user` and `repair` are lists of lines joined with `"\n"`. `{{name}}` is replaced by the value of
  `variables.name`, or by its `empty` text when the value is blank; values longer than `max_chars` are
  rejected before the call.
- Messages: the system text; then, per example, a user turn (`user` rendered with `example.input`) and an
  assistant turn (`example.output` as compact JSON); then the user turn for the real input.
- `call` holds the sampling settings (the drafter: temperature 0.2, max_tokens 1600). The reply is one JSON
  object that must pass `output.schema`; when it does not, the reply and `repair` (rendered with `{{errors}}`)
  are appended, at most `call.max_repairs` times.
- The system text and examples are the same for every call, so senders should mark them cacheable where the
  provider supports prompt caching.

The drafter asks for one self-contained question (noul or choice, never score) with descriptive option keys,
`what`/`not_for` descriptions and exactly one escape option, backticked state references only, no counting or
double negatives, `escalation.numeric_or_date` for checks on numbers or dates, parameters as `rules.<name>`,
corroborators from the registry or the detectors, six labelled test samples, a rationale and split suggestions.
Its three examples (a choice check with a parameter, a grounding check on dates that can block, and a
security check) are validated like drafts, so changing a rule in the system text means updating the examples.

## Demo scenarios

`demo/scenarios.v1.json` is the single source of demo and e2e traffic. A scenario is a complete,
deterministic story that every service reads, so a zero-key stack (`make demo`: mock decision backend, mock
judge, test mode) produces the same traces every time.

| Field | Meaning and consumer |
|---|---|
| `id` | Sent by `trafficgen` as `X-TrustAgent-Scenario` (honoured only with `TRUTHTABLE_TEST_MODE`). The mock decision backend (and mock-upstream's decision endpoints) look up `mock_answers` by it, and Go passes it on as `AuditOptions.mock_scenario` for the mock judge. |
| `sets` | Selection for `trafficgen --scenarios <set>` (and `--exclude`): `s0` (walking skeleton), `demo`, `e2e`, `untagged`, `generated`, `knowledge`, and a phase tag (below). |
| `route`, `headers`, `api_format`, `stream`, `request` | What `trafficgen` sends: `request` is the client body, with evidence placed where SPEC §2.10 extracts it; `headers` holds extra request headers (`X-TrustAgent-Route` selects the route). The body has the shape of its `api_format`: `openai_chat` has `messages` (which may hold `tool_calls` with `content: null` and `tool` messages), `anthropic_messages` has `messages` plus a top-level `system` (a string or text blocks), and `openai_completions` has a `prompt` and no `messages`. A consumer that reads requests itself (a Playground example list, a recording) picks the scenarios it can represent by `api_format`, `stream` and the phase and `knowledge` tags instead of assuming every body is a chat. |
| `answer_source`, `response` | The upstream answer. `scripted` answers go out as `test_response`, so no upstream is called; `generated` answers come from a real model when recording, and `response` is then the mock-mode stand-in. `trafficgen --upstream all` sends no `test_response`, and mock-upstream answers with `response` (JSON or SSE). |
| `mock_answers` | Raw answers the mock backend (`TRUTHTABLE_JEV_BACKEND=mock`, `TRUTHTABLE_JEV_MOCK_MODE=scenario`) returns, keyed by question id `<id>__v<version>` (SPEC §2.9 compile step 5) for each evaluator the route asks. Evaluators that compile excludes (for example `no_evidence`) are not asked and have no answer. |
| `fallback` | Only on a fallback route: the fallback answer (`response`), the raw answers to its re-gate (`mock_answers`, used when the state's `assistant_response` is the fallback answer) and the re-gate's expected decision (`expect`). In test mode, when the original answer is scripted (`test_response`) and `X-TrustAgent-Scenario` names the scenario, the gateway answers its fallback call with `fallback.response` and calls no upstream (the zero-key demo has none); otherwise it calls the upstream, and mock-upstream serves `fallback.response` to a request that carries the fallback prompt's `CONTEXT` block. |
| `knowledge` | Only on a route that reads the knowledge add-on: the knowledge-base documents `RetrieveContext` returns for this request (the knowledge profile must hold them). |
| `judge` | The mock judge fixture (`LLM_PROVIDER=mock`). `claims`, in response order, is the decomposer output (`claim` and a `quote` that is verbatim in `response`); each claim's `verdict`, `confidence`, `evidence` (verbatim from the request or the knowledge documents) and `reasoning` are its verifier output, which the deep audit reports unchanged. `null` means no LLM call may happen; the deep audit of the original answer is what counts, also after a fallback. |
| `expect` | The expected outcome: the gate decision and its `X-TrustAgent-*` values (`mode`, `action`, `would_action`, `status`, `verdict`, `max_risk`, `reasons`, `checked_against`, `audit`), the decision's `deep_audit` class, the deep-audit verdict and the dashboard outcome; plus what the client receives: `delivered_text` (the block message or the fallback answer, when it is not `response`), `http_status` (default 200) and, for a passthrough stream, `stream_decision` (the `: trustagent {...}` comment and the Mode and Action trailers). |

**How the expectations are checked.** Each scenario's `description` records its hand derivation from SPEC
§2.9. `make contracts-check` checks the parts that need no evidence extraction (routes, mock answers,
modes, outcomes, delivered text, judge quotes). The Go tests in `backend-go/cmd/trafficgen` replay every
scenario through the reference (route match, evidence extraction, detectors, compile, the scripted
answers, `decide()`, the header values, the audit plan, the fallback re-gate, the delivered text, and the
audit verdict scoring v2 gives the judge fixture) and send every scenario this build can serve through the
real `internal/gate` with the real mock backend. The `backend-go/cmd/proxy` scenario tests run `trafficgen
--expect` against the whole gateway in process, both as the demo stack (mock backend, scripted answers) and
as the e2e stack (compatible backend and LLM upstream on mock-upstream, `--upstream all`), and
`backend-python/tests/unit/test_demo_scenarios.py` runs every queued deep audit through the engine's
`Evaluate` with the mock judge. `trafficgen --expect` checks a running stack (`make demo-scenarios`,
`make e2e-scenarios`): the decision the response carries (headers; for streams also trailers and the
comment; for observe routes, whose headers say `deferred`, the stored trace), the delivered text, the
settled trace and its audit.

**Policies.** The routes live in `config/policies.yaml`, the policy the gateway loads (also in `make demo`),
enforcing demo routes `payments-faq` (fallback) and `help-center` (block) included, and in
`config/policies.pending.yaml`, which holds `handbook`: it reads the knowledge add-on, which the demo and
e2e stacks run without. Its routes merge over the defaults of `config/policies.yaml`; the gateway never
reads it. Every demo route audits each answer it may audit (`pass_sample_rate: 1.0`), draws no uniform
sample and stores every body, so runs are deterministic.

**Phases.** A scenario that needs a later gateway phase than the walking skeleton carries that phase as a
set tag: `p3` for streaming gating, `/v1/messages`, `/v1/completions`, block and fallback bodies, and routes
in `config/policies.pending.yaml`. `trafficgen` skips scenarios whose phase is later than `--phase`
(default: the phase this build implements, `p4`; no scenario carries `p4` yet), so a gateway of an earlier
phase can still be driven with `--phase p2`. With `--expect` a skipped scenario fails the check (exit status 1), because a check
that skips a scenario has not tested it; `--allow-skip` accepts the skips. The demo set sends 26 scenarios
(6 of them `p3`) and the e2e set 23. A Go test fails when a scenario's tags do not match its features.

**Calibration.** `config/calibration/mock__jev-heuristic-v1.json` is the calibration of the mock snapshot,
quality `mock`: an identity table with no labels behind it. It counts only with the mock backend, in demo
mode or a test-mode stack (SPEC §2.11), where it lets `payments-faq`, whose evidence checks adopt
calibrated thresholds, fall back instead of being capped to a flag. It claims nothing about any real
model; the e2e stack (compatible backend) does not use it, so `payments-fallback` is in set `demo` but not
`e2e`.

**Stacks.** `make demo` serves the pack with the mock decision backend and scripted answers
(`test_response`); `make demo-scenarios` checks it (`DEMO_SCENARIOS=s0` is the S0 gate). `make e2e-up`
starts the e2e stack (`docker-compose.e2e.yml`, project `truthtable-e2e`): the `compatible` decision backend
calls mock-upstream's `/v1/systemone` over HTTP, the OpenAI and Anthropic upstreams are mock-upstream too,
the judge is the mock provider, and traces are written before the response returns
(`TRUTHTABLE_TRACE_FLUSH=sync`). `make e2e-scenarios` sends set `e2e` with `--upstream all`, so every answer
takes the upstream path; `make e2e-down` removes the stack. Both targets send trafficgen's default phase (`p4`);
`DEMO_PHASE` and `E2E_PHASE` choose another.

## API fixtures

`fixtures/api/<Type>.<case>.json` holds one golden body per REST response type and WebSocket event of the
`api.v1` core subset (SPEC §2.4, §2.5). `<Type>` is the `api.v1` definition the body validates against
(`Page<T>` is written `Page-T`); WebSocket fixtures are `WsEvent.<type>[.<variant>].json`. msw handlers and
Go handler tests start from them, so they tell one consistent, production-like story:

- the three S0 demo scenarios on `support-bot` (flag mode) as live proxy traffic, gated by Jev 1.13 through
  OpenRouter (`typesafe/jev-1.13-20260917`) and audited by Claude Haiku: a grounded pass, the flagged 60-day
  refund answer with its gate decision and deep audit, and a trace with no evidence that was not checked;
- a direct audit whose answer starts with emoji, so its claim spans differ between UTF-16 code units and code
  points;
- the WebSocket lifecycle of the flagged trace (`trace_started` to `audit_completed`), plus `hello`, `hb`,
  `audit_failed`, `audit_dropped` and `gap`, and the error body for 400, 401, 404 and 503.

Ids are UUIDv7 whose time matches `created_at`; hashes, token counts and detector findings come from the Go
reference (the frozen `s0-*` compile vectors), costs from `pricing/prices.v1.json`, and audit scores from the
scoring v2 formulas (SPEC §3.2). When `api.ts` changes, regenerate `api.v1` and update the fixtures in the same
contract PR.

## Validation

```bash
make contracts-check     # npm ci when needed, then node validate.mjs
make contracts-test      # the validator's own tests (node --test)
make contracts-go        # go vet + go test for the embed module
make vectors             # Go cmd/vectorgen fills mechanical expected values (VECTORGEN_FLAGS=-check: fail on stale)
```

Without the root Makefile targets: `make -f mk/contracts.mk contracts-check`, or
`cd contracts && npm ci && node validate.mjs`. Add `--strict` to fail on warnings.

`validate.mjs` maps every file to a schema by path (a file with no mapping is an error), validates it,
and then runs the cross-file checks JSON Schema cannot express:

- evaluator hard rules: file name matches `id`/`version`; `risk_weights` keys are options;
  `risk_levels` are below the number of criteria; `escalate_from < warn_at <= critical_at`; backticked
  references resolve to a declared state field or `rules.<param>`; no question id in question text;
  `requires_corroboration` and `implies` name registered evaluators or known detectors;
- evaluator lints (SPEC §2.8): built-in templates are lint-clean, and every `lint` vector's `expected` is what
  the text hard rules and lints give for its spec (rules the SPEC names only by id follow the TypeScript
  reference, `frontend-react/src/lib/decision/lint.ts`);
- question sets, policies, presets and scenario mock answers reference registered evaluators (while
  `evaluators/` is still empty these refs are reported as warnings);
- presets: unique ids and names; a block or fallback preset buffers streams, can block (a block-eligible
  evaluator or `detectors.block_on`), attaches a corroborator for each block-eligible evaluator, and says in
  `ui_note` that it starts as Flag while `require_calibration` holds;
- prompts: the file name matches `id` and `version`; `{{name}}` placeholders and `variables` agree; examples
  supply exactly the user template's variables and pass `output.schema`; the first call fits the static
  playground's token cap; the drafter's system text names every state field, category and detector, and its
  examples pass the hard rules, are lint-clean and have 3 firing and 3 non-firing samples with exactly the
  state the question reads;
- policies: unique route names and evaluator ids, declared params unique per route, `evidence_sources`
  within the route sources, `hedge_after_ms` below `deadline_ms`, threshold order after overrides;
- pricing figures recompute from their terms; value claims match their figure, price entry or measured
  key;
- the key registry: unique names and aliases, valid defaults per kind, no secret defaults, `VITE_*`
  keys exactly the build keys and never secret, at most 15 non-advanced keys (`.env.example`);
- vectors: known kind, kind matches the directory, name matches the file; `decide` inputs match
  `decide-input.v1`; `lint` specs match `evaluator.v1` and `expected` lists known codes, sorted; pinned
  `detectors` findings select their text (UTF-16 offsets); `evidence` tag patterns are portable;
- API fixtures: the file name names an `api.v1` definition (`WsEvent.<type>[.<variant>].json` for events)
  and the fixture validates against it; every core response type and WebSocket event has a fixture; the
  parts of a trace carry its id; gate decisions also validate against `decision.v1`; claim spans, verified
  evidence spans and detector findings select the text they claim to (UTF-16 offsets);
- rules: every `{pattern, flags}` in `rules/` (and every policy `tag_patterns` entry) compiles in JS, uses
  only the flags `i`, `m` and `s`, and has no lookaround, backreference or inline flags (`go test` compiles
  the same patterns, and every schema `pattern`, with Go's RE2);
- scenarios: unique ids; a scripted or generated scenario has `response`; the request lands on the scenario's
  route in `config/policies.yaml` plus `config/policies.pending.yaml` (first match on headers, paths and
  models), and a route from the pending file needs a phase tag; `mock_answers` and `fallback.mock_answers`
  name questions that route asks, with the question's answer type, and `mock_answers` cover every evaluator
  that needs no evidence; `expect.mode` is the route's effective mode and the action fits it;
  `expect.outcome` is what `ui/outcomes.v1.json` gives; `expect.delivered_text` is what the route delivers
  (block message, fallback answer); `fallback` only on fallback routes, `knowledge` exactly on knowledge
  routes (with the `knowledge` tag), `stream_decision` only on streams, the `generated` set exactly the
  generated scenarios, no phase tag in `s0`; the deep-audit fields agree with `judge` (`NOT_ASSESSED` needs
  `judge: null`); judge quotes occur verbatim in `response` and verifier evidence verbatim in `request` or
  `knowledge`;
- UI: every outcome is reachable and the last rule is a catch-all; glossary `see_also`, `{command:}` and
  `{claim:}` references resolve; commands name real compose services and profiles;
- `superseded.v1.json` has the shape `scripts/check-forbidden.mjs` accepts, and no contract file uses one of
  its identifiers.

Repository files that follow a contract are validated too when present: `config/policies.yaml`
(`policy.v1`, the same policy checks, and the scenario checks above, which fall back to
`policies/example.policies.yaml` without it), `config/policies.pending.yaml` (`policy.v1`, only `version` and
`routes`, whose routes are checked merged over the defaults of `config/policies.yaml`), `config/calibration/*.json` (`calibration.v1`, plus a
non-decreasing table and quality rules) and `docs/benchmarks/results/*.json` (`benchmark-run.v1`).

## Changing contracts

`contracts/` changes only through contract PRs on the integration branch, owned by the lead
(SPEC §4.1). Each contract PR updates the affected vectors and fixtures, and the Go and TS runners must
be green. Service worktrees read contracts; they do not edit them.

## Superseded identifiers

`superseded.v1.json` lists identifiers that must never be implemented (SPEC Appendix A).
`scripts/check-forbidden.mjs` scans tracked code for them line by line (not `*.md` prose, `docs/archive/**`,
`docs/v2/**` or the list itself) and rejects unknown keys, so the file keeps exactly its format:
`{version: "1", description?, identifiers: [{area, pattern, kind, note, flags?, allow?, level?}]}`. A `literal`
pattern is a case-sensitive substring; a `regex` pattern is an ECMAScript RegExp source compiled with `flags`
(header names use `i`). `allow` lists repo-relative path globs where an identifier is permitted.

`level: "warn"` marks an identifier that legacy code still uses at P1, so the CI check reports it without
failing until the stream that owns that code removes it; that PR flips it to `error`. Today: `?api_key=`
(`backend-go/cmd/proxy/main.go`, `frontend-react/src/api/client.ts`), `VITE_TRUTHTABLE_API_KEY`
(`frontend-react/src/api/client.ts`) and the `audit-engine` compose service (`docker-compose.yml`,
`config/prometheus.yml`).
